# AGUS Phase 1 — architecture contracts v1

Date: 17 October 2026. Baseline: `a73d96c92d57df812485b66213689658e6c80391`.
Status: **proposed contracts for founder review; no implementation in this phase**.
Normative words below describe acceptance requirements for future work, not existing capabilities.

## 1. Integration boundary

Keep the existing Next.js application and separate two domains:

```text
Authenticated request -> server-owned principal + account grants
  -> read-only conversation planner -> validated tool registry
     -> financial-data service -> consent checks -> fixture source / future adapter
     -> bounded, attributed facts -> validated response -> persisted conversation

Payment intention -> existing editable proposal / unverified payment draft
  -> existing beneficiary verification -> reviewed digest + password approval
  -> separate explicit submission -> existing OTP and reconciliation engine
```

The read registry must not expose beneficiary creation, approval, submission, OTP,
payment retries, arbitrary HTTP, SQL, file access, or JavaScript execution. A user
request or provider description cannot add tools or grant permissions. Model-selected
payment preparation continues through the existing validated draft path; a read-tool
plan cannot invoke it. Missing draft details remain missing.

Preserve `src/lib/payments.ts`, `paystack.ts`, `auth.ts`, `config.ts`, payment types
and digests in `domain.ts`, and the existing mutation routes. New data records are
a separate read model, never substitutes for `Batch` or `Payment`. Read-only
lookups of existing payout evidence may use a sanitized projection with no nonce,
password, token, raw response or mutation capability. Any required payment-engine
change needs a separate proposal and authorization.

Do not populate bank history from a payout draft. Submission acceptance, signed
webhook delivery, provider-verified status, and recipient bank credit are different
evidence states. A Paystack payout balance is not a user's linked-bank balance.

## 2. Shared types and validation

Agent A owns `src/lib/financial-data/contracts.ts` and corresponding strict Zod
validators. Freeze that contract commit before Agent B imports it. The following
TypeScript-shaped definitions are the target wire/storage contract. IDs are opaque,
nonempty strings of at most 128 characters; timestamps are ISO 8601 UTC instants.
All objects reject unknown keys. Missing provider values are `null`, never invented.
Derived search fields are generated by trusted normalization, not accepted from a
provider/model unchanged. Fixture mode requires `simulated=true` and a nonempty
fictional label on every transaction and matching markers on accounts/evidence.
Sandbox data must retain its sandbox source even when it is not locally simulated;
never collapse sandbox and live into an unqualified success label. Reject inconsistent
source/mode/owner links at ingestion. Null hashes mean no artifact hash is available.

```ts
type Provider = "fixture" | "wema" | "mono" | "paystack_projection";
type DataMode = "fixture" | "sandbox" | "live";
type Scope = "accounts:read" | "transactions:read" | "evidence:read";
type Ownership = { tenantId: string; ownerId: string; accountId: string };
type PermissionContext = {
  tenantId: string;
  actorId: string;
  requestId: string;
  now: string; // trusted server clock, never supplied by the model
};
type Consent = {
  id: string;
  tenantId: string;
  ownerId: string;
  provider: Provider;
  mode: DataMode;
  accountIds: string[];
  scopes: Scope[];
  purpose: "financial_assistant";
  state: "active" | "revoked" | "expired";
  grantedAt: string;
  expiresAt: string;
  revokedAt: string | null;
  version: number;
};
type AccountRecord = Ownership & {
  provider: Provider;
  mode: DataMode;
  displayName: string;
  maskedNumber: string | null; // last four digits only
  currency: "NGN";
  consentId: string;
  simulated: boolean;
  lastSyncedAt: string | null;
};
type NormalizedTransaction = Ownership & {
  schemaVersion: 1;
  id: string;
  revision: number;
  currency: "NGN";
  amountKobo: number; // positive safe integer magnitude, never floating naira
  direction: "debit" | "credit";
  status: "pending" | "posted" | "failed" | "reversed" | "unknown";
  occurredAt: string | null;
  bookedAt: string | null;
  observedAt: string;
  updatedAt: string;
  counterparty: { displayName: string | null; institution: string | null };
  description: string; // <= 500 characters, untrusted provider data
  reference: string | null; // <= 128 characters, escaped for display
  category: { value: string; source: "fixture" | "provider" | "user" } | null;
  search: { normalizedText: string; tokens: string[]; version: 1 };
  provenance: {
    provider: Provider;
    mode: DataMode;
    providerTransactionId: string;
    providerAccountRef: string; // internal reference, not bank account digits
    consentId: string;
    fetchedAt: string;
    rawRecordRef: string | null; // restricted internal store reference
    rawRecordSha256: string | null;
    timestampBasis: "provider" | "fixture";
  };
  evidenceIds: string[];
  reversalOfId: string | null;
  simulated: boolean;
  simulationLabel: string | null;
};
type EvidenceRecord = Ownership & {
  id: string;
  transactionId: string;
  kind:
    | "synthetic_record"
    | "provider_record"
    | "transfer_verification"
    | "receipt_attachment";
  provider: Provider;
  mode: DataMode;
  sourceReference: string;
  observedAt: string;
  sourceStatus: string | null;
  artifactRef: string | null; // server-resolved restricted reference, not arbitrary URL
  sha256: string | null;
  limitations: string[];
  simulated: boolean;
};
type Coverage = {
  from: string;
  toExclusive: string;
  state: "complete" | "partial" | "unknown";
  missingAccountIds: string[]; // only already-authorized accounts
  undatedCount: number;
  lastSyncedAt: string | null;
  reasons: string[]; // bounded server codes, not raw provider prose
};
```

V1 is NGN only. Reject other currencies explicitly; do not label foreign minor
units “kobo” or add different currencies. Convert signed legacy fictional ledger
amounts into magnitude + direction in the new fixture adapter only. Do not alter
`LedgerEntry` or existing calculations in place. Validate every amount and each
sum with `Number.isSafeInteger`; fail on overflow. Zero-value records are excluded
from v1 monetary transactions with an explicit ingestion warning.

Use composite uniqueness on `(tenantId, ownerId, accountId, provider, mode,
providerTransactionId)`. Repeated ingestion updates revision/provenance rather than
creating another spend. Never deduplicate by amount/date/name alone. V1 assigns
one authoritative data source to each account; if two adapters represent the same
account, Gerald must resolve identity before aggregation. Do not silently combine
mirrored histories. Payout projections remain evidence-only and are excluded from
spending totals. Do not count both a reversed original and its returned funds as
ordinary spending/income. Keep reversal links and report reversal counts separately.

Proposed storage is separate indexed tables for accounts, consents, transactions,
evidence and conversation state. Agent A delivers the repository abstraction and
in-memory fixture implementation first; Gerald alone owns any SQL migration and
PGlite/PostgreSQL persistence wiring. Foreign keys must include tenant/owner/account
scope, including transaction-evidence links. Index scope + transaction date + ID,
and scope + reference/normalized search fields. Never extend the singleton payment
aggregate to pretend it is a multi-tenant banking database.

## 3. Consent-aware source interface

`src/lib/banking-data.ts` currently contains only `getAuthorizedHistory` and
`revokeConsent` declarations. Nothing implements it. Gerald will replace or re-export
the approved v1 interface during authorized integration; Agent A uses the new namespace.

```ts
type Page<T> = { items: T[]; nextCursor: string | null; coverage: Coverage };
type HistoryQuery = {
  accountIds: string[];
  from: string;
  toExclusive: string;
  cursor: string | null;
  limit: number; // 1..50 provider records per page
};
type AccountSummary = {
  accountId: string;
  currency: "NGN";
  availableKobo: number | null;
  currentKobo: number | null;
  asOf: string | null;
  simulated: boolean;
  unavailableReason: "not_provided" | "stale" | null;
};
interface BankingDataSource {
  readonly provider: Provider;
  readonly mode: DataMode;
  listAccounts(
    ctx: PermissionContext,
    consentId: string,
  ): Promise<AccountRecord[]>;
  getTransactions(
    ctx: PermissionContext,
    consentId: string,
    query: HistoryQuery,
  ): Promise<Page<NormalizedTransaction>>;
  getTransaction(
    ctx: PermissionContext,
    consentId: string,
    accountId: string,
    transactionId: string,
  ): Promise<NormalizedTransaction | null>;
  getEvidence(
    ctx: PermissionContext,
    consentId: string,
    accountId: string,
    transactionId: string,
  ): Promise<EvidenceRecord[]>;
  getAccountSummary(
    ctx: PermissionContext,
    consentId: string,
    accountId: string,
  ): Promise<AccountSummary>;
  revokeConsent(ctx: PermissionContext, consentId: string): Promise<void>;
}
```

`revokeConsent` is an authenticated administrative operation outside the model tool
registry. Deny locally before attempting remote revocation; record pending remote
revocation safely. Consent creation/token exchange also stays outside the registry.
The adapter obtains credentials from a server-side resolver; no token in these types.

The service checks active consent, expiry, mode, scope, account membership and
actor access before each adapter call, cache lookup and response/model disclosure.
Listing accounts/summary requires `accounts:read`; transaction/search/calculation
requires `transactions:read`; evidence requires both `transactions:read` and
`evidence:read`. No implied scopes. Bind each account to its own active consent;
multi-account reads validate all bindings before returning any data.
Adapters independently verify ownership; a caller-supplied account ID is not access.
Recheck consent version after provider I/O. Revocation invalidates cursors, cached
facts and contextual selections immediately. Already-transmitted model data cannot
be recalled; disclose this before any future real-data model use. Grant expiry uses
the trusted clock even if the persisted state still says `active`.

Fixture source has a server-created, clearly fictional grant and scoped fictional
accounts; it must not claim Wema/Mono consent was obtained. Wema and Mono remain
unsupported adapters until official contracts, legitimate sandbox access and
account-level verification exist. Return `UNSUPPORTED_CAPABILITY`, never fixture
fallback after provider failure. No automatic provider selection from bank names.

Pagination uses opaque adapter cursors; no model-visible provider cursor or URL.
Enforce deadlines, cursor-cycle/no-progress detection, duplicate IDs and schema
validation. Missing provider fields remain unknown with coverage reasons. Fixtures
support a fixed seed and injected clock so dates and expected totals are reproducible.

## 4. Read-only tool protocol

Server injects `PermissionContext` and authorized consent bindings. Model arguments
must not include actor, tenant, owner, consent, mode or credential fields. Every tool
gets a strict runtime validator and a typed dispatcher; unknown tools fail closed.
Common `ReadFilter` fields are:

```ts
type ReadFilter = {
  accountIds: string[]; // 1..5, subset of server-authorized IDs
  from: string;
  toExclusive: string; // required; <= 366 days
  direction?: "debit" | "credit";
  statuses?: ("pending" | "posted" | "failed" | "reversed" | "unknown")[];
  category?: string; // exact known category, max 50 characters
  amountKobo?: { min: number; max: number }; // inclusive, safe integers
};
type ToolArgs = {
  search_transactions: ReadFilter & {
    query: string;
    limit: number;
    cursor: string | null;
  };
  get_transaction: { accountId: string; transactionId: string };
  calculate_spending: ReadFilter & {
    groupBy: "none" | "category" | "week" | "month";
  };
  find_payment_evidence: { accountId: string; transactionId: string };
  get_account_summary: { accountIds: string[] };
};
type ToolCall<K extends keyof ToolArgs> = {
  protocolVersion: 1;
  callId: string;
  name: K;
  args: ToolArgs[K];
};
type ToolErrorCode =
  | "INVALID_ARGUMENT"
  | "NOT_FOUND"
  | "PERMISSION_DENIED"
  | "CONSENT_REQUIRED"
  | "CONSENT_EXPIRED"
  | "CONSENT_REVOKED"
  | "UNSUPPORTED_CAPABILITY"
  | "PROVIDER_UNAVAILABLE"
  | "TIMEOUT"
  | "CURSOR_INVALID"
  | "SNAPSHOT_EXPIRED"
  | "LIMIT_EXCEEDED";
type ToolResult<T> = {
  protocolVersion: 1;
  callId: string;
  outcome: "ok" | "empty" | "partial" | "error";
  data: T | null;
  error: { code: ToolErrorCode; retryable: boolean } | null;
  meta: {
    resultId: string;
    asOf: string;
    coverage: Coverage | null;
    simulated: boolean;
    sources: { provider: Provider; mode: DataMode }[];
    truncated: boolean;
    nextCursor: string | null;
    warnings: string[];
  };
};
```

`callId` is unique per turn, max 64 characters. `query` is 0..200 characters,
`limit` defaults to 10 and is 1..25. Account arrays cannot contain duplicates.
`from < toExclusive`; timestamps are explicit instants. Date language is resolved
against a server clock and `Africa/Lagos`; ask a question when “last Friday”,
“about 50k” or account scope is ambiguous. An approximate amount requires a stated,
user-confirmed tolerance; the executor never silently broadens filters.

| Tool                    | Required result data and semantics                                                                                                                                                                                                                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `search_transactions`   | `matches: TransactionView[]`, applied filters, rank reasons and `hasMore`. Each view contains ID, account ID, masked account label, dates/date basis, direction, amount, currency, status, counterparty, description, category, simulation marker and safe source references. No secrets, raw records, full account numbers or artifact URLs. |
| `get_transaction`       | One authorized `TransactionView`, its revision and safe evidence references; absence and cross-owner IDs both use `NOT_FOUND` without disclosing existence.                                                                                                                                                                                   |
| `calculate_spending`    | Currency, exact applied interval/timezone/filters, `expenseKobo`, `incomeKobo`, `netKobo`, groups with counts, included count, excluded status/reversal/undated counts, coverage and an immutable calculation ID. Never compute from the model's first page.                                                                                  |
| `find_payment_evidence` | At most 10 safe evidence views with kind, source, source reference, observed time, simulation flag and limitations. No available evidence returns `empty`, not a fabricated receipt. Artifacts open only through a separately authenticated server resolver.                                                                                  |
| `get_account_summary`   | At most 5 account summaries with source, freshness and known/missing balances. Available/current may be signed safe integers. Unknown balance is `null`, not zero and not the sum of incomplete history. Never read the Paystack payout balance as a personal account summary.                                                                |

Search v1 is deterministic: Unicode NFKC, lowercase, collapse whitespace, tokenize
letters/digits, then AND-match tokens against counterparty, description and reference.
No arbitrary regex/SQL, vector database or guessed semantic equivalence. Rank exact
reference first, exact counterparty second, remaining token matches third; ties use
transaction time descending (bookedAt, otherwise occurredAt; null last), then ID
ascending. Return rank reasons. A vague request can become a structured filter via
the planner, but unsupported semantic matches must be disclosed. Ask to refine a
zero-result query; do not assert that a payment never happened.

Search cursors are server-issued opaque references to a 15-minute query snapshot,
bound to principal, consent version, mode, filter hash, stable ordering and selected
record revisions. New ingestion cannot skip/duplicate rows mid-page; expire the
snapshot on relevant updates. Tampering, reuse by another actor or filter changes
fail. Fetch maximum 50 records per adapter page, maximum 100 pages / 5,000 records
per calculation. Stop on cycles/timeouts. A budget overflow returns `LIMIT_EXCEEDED`
and asks for a narrower interval; it must not publish partial arithmetic as a total.

Spending defaults to posted debits only; income is posted credits. Pending, failed,
unknown and reversed transactions are excluded and counted explicitly. A linked
reversal credit is excluded from ordinary income. Net = income minus expenses.
For `calculate_spending`, reject a requested status other than `posted` as
`INVALID_ARGUMENT`; searching pending/failed items is supported separately. A
direction filter can narrow the corresponding income/expense calculation and must
be displayed with the result so a debit-only query is not described as net cashflow.
No fee estimates or payment drafts enter these totals. Apply filters before grouping.
Weeks start Monday 00:00 WAT; months start local day 1. Intervals are half-open
`[from,toExclusive)`. Missing both provider timestamps excludes a record from dated
totals with an undated warning; never date it by retrieval time. Incomplete source
coverage produces `partial` and the wording “available records”; a complete zero-row
query may return zero, while absent access or absent coverage cannot.

## 5. Planner, executor and grounded language

Agent B owns a discriminated planner decision:

```ts
type Decision =
  | {
      kind: "clarify";
      reason: "account" | "date" | "amount" | "selection";
      question: string;
    }
  | { kind: "call_tool"; call: ToolCall<keyof ToolArgs> }
  | { kind: "respond"; response: GroundedResponse };
type GroundedResponse = {
  kind: "answer" | "no_results" | "ambiguous" | "unavailable";
  segments: (
    | { type: "text"; text: string } // nonfinancial connective language only
    | { type: "fact"; resultId: string; path: string }
  )[];
  selectedTransactionIds: string[];
};
```

In implementation, `ToolCall` must be a mapped discriminated union so `name` and
`args` remain correlated; do not implement the sketch as an uncorrelated union.
Fact paths are a server allowlist into current-turn sanitized results, never arbitrary
object traversal. A typed facts catalogue formats money, status, dates and evidence
limitations. All financial clauses render from fact segments or server templates.
Do not re-enable unrestricted `response`/`clarification` prose from the existing
model plan: PR #9 repaired fabricated financial narration. Text segments must be
limited to approved connective phrases/questions in v1; a regex that merely rejects
digits cannot establish grounding. Reject uncited financial assertions and fall back
to the deterministic renderer. Later freer prose needs separate adversarial evidence.

One turn can make up to 5 sequential read-tool calls and 6 model calls, within a
60-second end-to-end deadline. Set each read call to at most 10 seconds and model
attempt to at most 20 seconds, each clipped to remaining time. Existing 45-second
inference defaults are not a suitable new-loop budget; Agent B's new adapter wrapper
must enforce the remaining budget without changing payment retries. Return at most
16 KiB sanitized JSON per result and 48 KiB total per turn; truncate views explicitly,
never silently truncate a calculation and call it complete. Limit context to the last
16 scoped messages / 12 KiB plus validated selections and result summaries; no hidden
chain of thought is requested or persisted. Model HTTP retries count toward budget;
no implicit tool retries, and repeated identical tool calls are rejected in a turn.

Example: “Find Ada's payment last week” -> clarify account if necessary ->
`search_transactions` -> two candidates -> ask which one -> persist candidate IDs ->
“the smaller one” -> revalidate scoped candidates -> `get_transaction` ->
`find_payment_evidence` -> explain what the returned source establishes and omits.
Never pick one candidate merely because it ranks first. A follow-up asking for a
total calls the calculator over the full filtered source, not the displayed matches.

Persist context separately with tenant/actor/conversation IDs, revision, selected
account/transaction IDs, explicit filters, candidate-set result ID, source revisions,
grant version and expiry. Use compare-and-swap on concurrent turns; reject stale
selection with a clarification. Default selections expire after 15 minutes. Reload
must not lose an unfinished selection. Recheck all IDs/access on every follow-up;
previous assistant prose is not evidence. Consent revocation or changed provider
revision invalidates selection. Retention policy and deletion controls remain a
real-data release gate; do not migrate legacy ownerless messages into scoped context.

Treat user messages, imported descriptions, receipt text, image OCR, prior model
answers and provider errors as untrusted data. They cannot override system rules,
select another actor, request credentials or expand the registry. No credentials,
full bank details, provider payloads or arbitrary URLs in model context/logs. Record
only request/tool names, counts, durations, safe error codes, model identifier,
simulation/provenance and hashed correlation IDs. Never log prompts or raw responses.
Escape UI and CSV output. A transport failure produces an explicit unavailable
response, never a successful mocked answer. The demo parser stays separately labelled.

## 6. Account isolation and rollout

Current authentication is **one configured operator**, not multi-user identity.
Existing batch ownership checks are valuable but the global ledger, ownerless legacy
messages and provider audit projection are not tenant isolation. In the first authorized
implementation, map the existing authenticated operator to one explicit demo tenant
and scoped fictional accounts on the server; do not accept actor IDs from the browser.
Test two principals against the service abstraction without claiming multi-user login.

Real Personal/Business account switching, roles and delegations need a later identity
and membership design. Shared platform means shared contracts, not shared balances,
consents or conversation. No real personal account ingestion until identity, retention,
consent, adapter and model-data-policy reviews have passed. Current global `/api/state`
data must not receive real bank records. Gerald owns a separate authenticated read
route and stores only scoped new context. The existing demo ledger can remain labelled.
